# Firecrawl、Crawl4AI、Browser Use 怎么选：采集与交互对比

> 最后核验：2026-10-21。依据官方功能说明选型，未宣称四个项目存在统一实测性能排名。

[← 返回教程总目录](../教程总目录.md)

## 先问：需要读网页，还是操作网页

把网页转成 Markdown，重点是内容覆盖、清洗和批量调度；登录后填表、点击并检查结果，重点是页面状态和动作控制。这两类任务可组合，但不应一开始都交给自由操作浏览器的 Agent。

| 工具 | 主要定位 | 最适合的第一项测试 |
|---|---|---|
| Firecrawl | 托管 / 开源网页内容 API | 单页 scrape 后核对正文 |
| Crawl4AI | 可本地运行的网页采集库 | 同页转 Markdown 与清洗 |
| Browser Use | 模型驱动浏览器 Agent | 完成自己的测试站交互目标 |
| agent-browser | 面向 Agent 的浏览器 CLI | snapshot、定位、操作、截图 |

## 1. 四个典型场景

**给知识库导入 50 页公开文档：** 先评估 Firecrawl 或 Crawl4AI，限制路径和页数，保留来源与哈希。

**给 Agent 做前端回归：** 优先 agent-browser 或测试工具，按真实页面状态验证。

**用自然语言完成多步网页任务：** 评估 Browser Use，明确允许动作和停止条件。

**只查询服务数据且有正式 API：** 直接用 API，减少页面选择器和状态维护。

## 2. 部署与费用

Firecrawl 托管服务需要对应账户和 Key；自部署要核对开源版支持范围。Crawl4AI 本地库需要浏览器和计算资源，云选项另算。Browser Use 自运行需要模型调用、浏览器与环境资源；agent-browser 的 CLI 执行也可能由外部模型驱动。

不要把“不需要购买软件”写成“运行没有任何成本”。具体额度与价格以当日官方方案为准。

## 3. 建一个公平测试集

为你拥有或获准测试的页面准备：静态正文、动态正文、分页列表、表格页面和带弹窗页面。每个样本定义预期标题、核心段落、字段与页面状态。

交互案例单独建立，例如测试站内搜索；不要拿抓取器和浏览器 Agent 的不同任务耗时直接做榜单。

## 4. 内容采集指标

| 指标 | 如何判断 |
|---|---|
| 正文覆盖 | 标注段落是否都存在 |
| 噪声 | 导航、广告和页脚占比 |
| 结构 | 标题、表格、列表和代码是否正确 |
| 来源 | URL、采集时间和内容哈希是否保留 |
| 成本 | 有效页面的总费用与人工修正成本 |
| 稳定性 | 相同输入重复运行是否一致 |

HTTP 成功但抓到验证码，应记失败；空输出也不能计入成功页面数。

## 5. 交互任务指标

定义起始状态、允许动作、成功状态和超时。记录 Agent 是否找对元素、是否填写正确、是否处理遮挡、是否产生额外副作用，以及最终结果能否验证。

页面变化后重新观察。旧快照引用不是永久元素 ID，点击命令执行成功也不是业务验收。

## 6. RAG 数据管道

```text
确定 URL 范围 → 采集 → 正文清洗 → 去重
→ 保留来源 → 切块 → Embedding → 检索验收
```

网页更新时根据哈希与更新时间更新索引；页面删除时处理旧向量。相同文档的多个 URL 应做规范化，避免检索结果被重复页面占满。

## 7. 常见误区

- 把浏览器截图当作结构化数据全集。
- 认为爬虫抓到 HTML 就一定获得动态正文。
- 把本地库能力和云服务能力写成完全相同。
- 把高并发测试结果写成对所有站点通用。
- 忽略模型、浏览器、抓取服务的不同 Key 和账单。

## 8. 选择后的最小验收

先完成 10 页或 5 个交互案例，保留失败样本。达到质量与预算要求后再扩大。限制 URL、权限和输出范围；网页中的指令不能覆盖用户目标。

需要真实登录的任务使用专门测试账户。浏览器状态和抓取原始内容可能包含个人信息，不随文档发布。
